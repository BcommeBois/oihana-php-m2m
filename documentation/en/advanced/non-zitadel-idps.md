# Non-Zitadel identity providers

`M2MApiClient` defaults to [Zitadel](https://zitadel.com)'s conventions, but the underlying flow ([RFC 7521](https://datatracker.ietf.org/doc/html/rfc7521) + [RFC 7523](https://datatracker.ietf.org/doc/html/rfc7523) `urn:ietf:params:oauth:client-assertion-type:jwt-bearer`) is a standard. Most modern OAuth2 / OIDC providers support it, with two adjustments at most :

1. The **token endpoint path** (`tokenPath`).
2. The **scope** requested at the token endpoint (`scope`).

Both are configurable via constructor arguments — no fork required.

## Provider matrix

| Provider           | `tokenPath`                                       | `scope`                                                | Identifier field            |
|--------------------|---------------------------------------------------|--------------------------------------------------------|-----------------------------|
| Zitadel (default)  | `/oauth/v2/token`                                 | `openid` + `urn:zitadel:iam:org:project:id:<id>:aud`   | `userId` (Service User)     |
| Auth0              | `/oauth/token`                                    | `openid profile` + your API audience                   | `clientId` (M2M application)|
| Keycloak           | `/realms/{realm}/protocol/openid-connect/token`   | `openid` + custom scopes                               | `clientId`                  |
| Generic RFC 7523   | per provider documentation                        | per provider documentation                             | `clientId` or `userId`      |

## Zitadel (default)

No configuration needed. The keyfile generated by Zitadel for a Service User is auto-sufficient.

```php
use oihana\m2m\M2MApiClient;

$client = M2MApiClient::fromKeyfile( '/secrets/zitadel-keyfile.json' ) ;
```

## Auth0

Auth0 supports the jwt-bearer grant for Machine-to-Machine applications. The token endpoint is `/oauth/token` (without `v2`).

```php
use oihana\m2m\M2MApiClient;

$client = M2MApiClient::fromKeyfile
(
    keyfilePath : '/secrets/auth0-keyfile.json' ,
    tokenPath   : '/oauth/token' ,
    scope       : 'openid profile read:widgets write:widgets'  // your API permissions
) ;
```

For the keyfile JSON, structure it manually since Auth0 doesn't emit the same shape :

```json
{
    "type":        "auth0-m2m",
    "keyId":       "your-auth0-key-id",
    "key":         "-----BEGIN RSA PRIVATE KEY-----\n…\n-----END RSA PRIVATE KEY-----\n",
    "clientId":    "your-auth0-application-clientId",
    "issuer":      "https://your-tenant.eu.auth0.com",
    "audience":    "https://api.example.com",
    "scope":       "openid profile read:widgets",
    "apiBaseUrl":  "https://api.example.com"
}
```

> Auth0 requires you to register the application's signing key in the Auth0 dashboard (Applications → Settings → Advanced → Endpoints). The `keyId` you supply must match the one registered there.

## Keycloak

Keycloak organises OAuth endpoints per realm. The token endpoint is `/realms/{realm}/protocol/openid-connect/token`.

```php
use oihana\m2m\M2MApiClient;

$client = M2MApiClient::fromKeyfile
(
    keyfilePath : '/secrets/keycloak-keyfile.json' ,
    tokenPath   : '/realms/my-realm/protocol/openid-connect/token'
) ;
```

Keyfile shape :

```json
{
    "type":        "keycloak-m2m",
    "keyId":       "your-keycloak-key-id",
    "key":         "-----BEGIN RSA PRIVATE KEY-----\n…\n-----END RSA PRIVATE KEY-----\n",
    "clientId":    "your-keycloak-clientId",
    "issuer":      "https://keycloak.example.com",
    "audience":    "your-keycloak-clientId",
    "scope":       "openid profile",
    "apiBaseUrl":  "https://api.example.com"
}
```

Configure the Keycloak client for **Signed JWT** authentication and upload the public key in the client's Credentials tab.

## Generic RFC 7523 provider

Any OAuth2 provider that supports `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer` works the same way. Read your IdP's documentation to find :

- The token endpoint path.
- Whether they expect `iss` and `sub` to be the `clientId` (registered application) or a user identifier (service account).
- The required scope syntax (some require an explicit `audience` parameter, which Zitadel encodes via the `urn:zitadel:iam:org:project:id:<id>:aud` scope).

## What is NOT configurable (yet)

The current v1.0 release hard-codes:

- The grant type (`urn:ietf:params:oauth:grant-type:jwt-bearer`).
- The signing algorithm (`RS256`).
- The token endpoint request format (form-encoded body with `grant_type` + `scope` + `assertion`).

If you need a different grant type (`client_credentials` with `client_assertion`), a different signing algorithm (`RS512`, `ES256`), or a different request format, **subclass `M2MApiClient` and override `getToken()`** — see [extending-the-client.md](extending-the-client.md).

Contributions to make these configurable in v2.0 are welcome — open an issue at [github.com/BcommeBois/oihana-php-m2m/issues](https://github.com/BcommeBois/oihana-php-m2m/issues).
